# 基准

后面每一项性能工作都拿这里的基线来比。基线是 `a78f490` 加上基准程序和 CPU 侧计时测的，还没有修正 `RenderWorld::validate`（见最后一节）。

## 怎么跑

```bash
tools/fetch-scenes.sh                      # 场景下载到 build/scenes，git 校验每个文件的哈希
cmake --preset release && cmake --build build/release
tools/run-benchmarks.sh nvidia build/bench     # 1920x1080，名字含 NVIDIA 的设备
tools/run-benchmarks.sh lavapipe build/bench   # 960x540，llvmpipe
```

`run-benchmarks.sh` 跑下面表格里的每一项，各写一个 JSON。单独测一项用 `build/release/probes/lrender_bench`，参数见它的 `--help` 输出和源码开头的说明；A/B 对比写成多个 `--config <名字>:<设置>=<值>,...`，比如 `--config shared:aliasing=on --config separate:aliasing=off`。

## 场景

| 名字 | 内容 | 测的是什么 |
|---|---|---|
| sponza | Khronos 示例里的 Sponza（Crytek 版）：103 个网格和实例，262,267 个三角形，25 种材质（植物用 alpha 遮罩），69 张纹理 | 室内建筑，纹理多，三角形大小不一 |
| game | Khronos 示例里的 ABeautifulGame：15 个网格、49 个实例，150 万个三角形，43 张纹理 | 密集的小三角形 |
| scale | `lr::examples::makeScaleScene`：地面上每 2 米一格放一个盒子、柱子或球（四种网格、16 种不带纹理的材质，随机转向和缩放），默认 256 盏有范围的点光源，一个投影的太阳。实例数、灯数、球的细分都可调；10 万个实例约 860 万个三角形，100 万个约 8600 万 | 实例数和灯数的规模；相机低，视线贴着地面，大部分物体被前面的挡住 |

路线图原本写的是 Intel Sponza 和 Amazon Bistro。Bistro 的原始发布是 FBX，asset 不读；Intel 的新 Sponza 体积很大。两者换成了 ABeautifulGame（密集几何）和规模场景（大量实例和灯）。两个 glTF 场景从 glTF-Sample-Assets 的固定提交下载，只取这两个目录。

## 方法

- **配置交替。** 每个 `--config` 有自己的 Renderer，都在同一个设备上。它们的帧一帧一帧轮流，每帧等它完成再提交下一帧，所以 GPU 频率怎么变，对各个配置的影响都一样。
- **预热。** 计时之前，每个配置先从轨道起点的相机渲染至少 60 帧，直到最近两个 30 帧窗口的中位数相差不到 2%（最多再加 600 帧）。这时 GPU 已经升到 P0，纹理也都流完了。纹理转换用 `Deterministic`。
- **相机。** 计时的帧绕场景相机的目标转一整圈，共 240 帧。同一个帧号上每个配置用同一个相机，第一帧标为相机切换。
- **输出。** 帧送到窗口目标，它的 Presenter 直接丢掉，走的是现在窗口用的 Readback 路径：最后一个 pass 写进映射内存。
- **指标。**
  - `gpu`：一帧里每个 pass 设备耗时之和。计时器打开时，tc 在每次 dispatch 前插入完整屏障，所以这是 dispatch 串行之后的时间。
  - `wall`：`FrameResult::wallTime`。
  - `prepare`、`record`、`finish`：`FrameResult` 的三段主机时间。
  - 每项都报告中位数和 p10、p90。另外报告帧图显存（`graphBytes`），以及最后一帧的可见实例和三角形数。
  - 在 NVIDIA 上，测量前后各用 `nvidia-smi` 记一次性能状态和频率，写进 JSON。
- **可重复性。** scale 场景 10 万个实例，同一配置连跑三次，每次 600 帧：
  - GPU 帧时间相差 1.9%，墙钟相差 2.2%；
  - GPU 线程的录制时间相差 0.7%；
  - 渲染线程的准备时间相差 4.5%。这台机器的 CPU 调频策略是 powersave，同时还有别的负载。
  - 每次 240 帧时，GPU 帧时间相差 0.7%。

## 读出来的结论

1. **真实场景上，阴影是最大的一块。** Sponza 的三级阴影占 GPU 帧的 57%（0.64 ms），在 lavapipe 上占 81%（45 ms）。每一级都光栅化整个场景：实例级剔除只能去掉级联之外的实例，而 Sponza 的实例都很大。所以 P4 要先做阴影投射物的按簇剔除；静态物体的阴影缓存（F4）也值得做。
2. **实例一多，压缩可见实例就成了大头。** 100 万个实例时四次压缩共 15.1 ms，每次 3.5 到 4.6 ms；10 万个时 1.4 ms。这就是 P2。
3. **规模场景的可见性光栅化。** 100 万个实例时可见性光栅化要 16.3 ms，可见三角形有 7366 万个。这些三角形大部分被前面的物体挡住，这是 P4 的遮挡剔除要去掉的。
4. **GPU 线程每帧的录制。** NVIDIA 上每帧要 0.7 到 1.1 ms，几乎和场景大小无关：路径追踪的帧只有三个 pass，也要 0.7 到 0.8 ms。lavapipe 上是 0.3 ms。这放进 P7 去查。
5. **渲染线程的准备时间随实例数线性增长。** 10 万个实例时 4.3 ms，100 万个时 33 ms，可是场景每帧都没有变。原因是 `RenderWorld::validate` 每帧都把世界里的所有 id 复制进新的哈希集合。

## 修正：增量的检查只看增量

`RenderWorld::validate` 改为在世界已有的索引里查，再加上增量自己 upsert 的 id，不再复制整个世界。检查的内容和报错的先后都没变。新加的测试覆盖了删除世界里已有的和同一个增量里刚加的实例、灯，也覆盖了删除不存在的对象。

| 场景 | 准备 | 墙钟 |
|---|---|---|
| scale，10 万个实例 | 4.35 → 0.028 | 8.85 → 4.41 |
| scale，100 万个实例 | 33.3 → 0.092 | 66.3 → 33.1 |

## P1：桌面零拷贝上屏

`present=` 设置把帧交给 offscreen 的 `VulkanPresenter`：它有自己的设备，帧拷进它自己的 BGRA 图像，不经过交换链。RTX 5070 Ti，Sponza 1920×1080，开计时器，240 帧：

| 配置 | GPU 帧 | 墙钟 | 收尾 | 上屏 |
|---|---|---|---|---|
| drop（Presenter 直接丢掉，基线的做法） | 1.115 | 2.63 | 0.055 | — |
| shared（SharedBuffer 路径） | 1.218 | 2.78 | 0.056 | 240 帧全部走 SharedBuffer，没有丢帧，交出到上屏 0.12 ms |
| readback（Readback 路径） | — | 242 | 232 | 交出到上屏 0.18 ms |

- 两者的先后对调、跑 480 帧，shared 对 drop 是 1.204 对 1.095 ms。多出的约 0.1 ms 分散在所有 pass 上，每个不到 3 µs，像是两个设备的上下文轮流占用 GPU 的代价。
- readback 的收尾慢在主机读回：tc 的 `createBuffer` 在开了 resizable BAR 的显卡上把回读 buffer 放进显存，主机读 8 MB 要 153 ms，缓存的系统内存只要 0.29 ms（`library-requirements.md` 第 5 项）。离屏目标同样受影响。readback 配置让 GPU 闲下来降到 P8，同一个进程里的其他配置也跟着变慢，所以表里它是单独测的。

## P2：并行压缩可见实例

RTX 5070 Ti，scale 场景，1920×1080，release，240 帧。压缩前后可见实例列表逐项相同（测试比对 30 万个实例时的整张列表）。

| 实例数 | 四次压缩 | GPU 帧 | 墙钟 |
|---|---|---|---|
| 10 万 | 1.416 → 0.038 | 3.56 → 2.08 | 4.41 → 4.23 |
| 100 万 | 15.08 → 0.084 | 32.0 → 16.4 | 33.1 → 22.3 |

墙钟的“之前”是修正 `validate` 之后的数。100 万个实例时，剩下的 GPU 时间几乎都是可见性光栅化（16.3 ms），这是 P4 的事。

## P3：簇和场景显存

`FrameResult::sceneMemory` 报告场景的设备内存，`lrender_bench` 打印出来并写进 JSON。RTX 5070 Ti：

| 场景 | 几何 | 簇 | 网格、实例、材质、灯光 | 纹理池 |
|---|---|---|---|---|
| sponza | 9.0 MiB | 0.3 MiB | 不到 0.1 MiB | 682.7 MiB |
| game | 18.0 MiB | 1.0 MiB | 不到 0.1 MiB | 1365.3 MiB |
| scale，100 万个实例 | 不到 0.1 MiB | 不到 0.1 MiB | 152.0 MiB | 0 |

纹理池是大头：每张纹理都重采样成 2048² 以内的 2 的幂正方形 RGBA8，带完整的 mip 链（2048² 一层 22.4 MB），池满了层数翻倍，所以还会多出空层。桌面上按 BC 格式烘焙（`preferKtx2`）能省到四分之一；按显存预算降低远处纹理的 mip 是 R5 的事。

## P4a：簇的视锥和背面剔除

`clusters=on|off`，同一进程里交替，RTX 5070 Ti，1920×1080，240 帧。

| 场景 | 簇（开 / 关） | 三角形（开 / 关） | GPU 帧（开 / 关） | 可见性光栅化 | 每级阴影光栅化 |
|---|---|---|---|---|---|
| sponza | 3198 / 3471 | 238,517 / 262,267 | 1.218 / 1.222 | 0.279 / 0.284 | 0.09–0.30，几乎不变 |
| game | 15,289 / 20,121 | 1,178,833 / 1,500,224 | 1.287 / 1.580 | 0.266 / 0.333 | 0.254 / 0.330 |

簇是三角形按索引顺序的连续区间（P3）。UV 球、按环排列的网格，簇是整圈的带子，法线锥张得太开，背面剔除用不上；Sponza 的大块墙面和地面也是这样。空间上更紧凑的切法要重排三角形，留到遮挡剔除之后按测量决定。

## 回读改用主机缓存的内存（tc `efc7d78`）

帧图的回读 buffer 改成 `createBuffer(n, tc::HostAccess::Reads)`，落在主机缓存的系统内存里。RTX 5070 Ti，Sponza 1920×1080：

| 配置 | 色调映射（最后一个 pass） | GPU 帧 | 收尾 |
|---|---|---|---|
| readback，之前（回读 buffer 在显存里） | 0.017 | 1.12 | 232 |
| readback，之后 | 0.74 | 1.87 | 0.57–0.90 |
| shared（SharedBuffer 路径，不受影响） | 0.018 | 1.31 | 0.026 |

最后一个 pass 现在经 PCIe 把 8 MB 写进主机内存，要 0.74 ms；主机读它只要不到 1 ms，原来要 232 ms。离屏目标同样如此。从这里起，`present=drop` 的帧也写进主机内存，它的 GPU 帧时间比前面各节的基线多 0.7 ms 左右，和之前的数比较时要扣掉。以后可以让最后一个 pass 写设备内存，再由传输队列异步拷到主机，GPU 的 compute 不必等 PCIe。

## P4b：两遍 HiZ 遮挡剔除

`occlusion=on|off`（两边都开着簇剔除），同一进程里交替，RTX 5070 Ti，1920×1080，240 帧的环绕。可见性光栅化一栏，开时是两张列表各自的光栅化。

| 场景 | 三角形（开 / 关） | 可见性光栅化（开 / 关） | GPU 帧（开 / 关） | 帧图内存（开 / 关） |
|---|---|---|---|---|
| scale，100 万个实例 | 2,182,394 / 73,658,541 | 1.119 + 0.143 / 16.092 | 3.120 / 17.850 | 191.6 / 155.9 MiB |
| scale，10 万个实例 | 820,295 / 7,375,088 | 0.339 + 0.157 / 1.603 | 1.751 / 2.864 | 64.5 / 64.5 MiB |
| sponza | 23,905 / 238,517 | 0.233 + 0.017 / 0.277 | 1.982 / 1.951 | 60.5 / 60.5 MiB |
| game | 1,140,973 / 1,178,833 | 0.251 + 0.019 / 0.267 | 2.100 / 2.049 | 60.5 / 60.5 MiB |

遮挡剔除每帧的固定开销约 0.07 ms：建金字塔 0.034 ms（11 级，每级一个 dispatch），第二阶段的剔除 0.007 ms、压缩 0.010 ms，第二张列表几乎为空时光栅化也要 0.017 ms（4 次 dispatch）。GPU 线程的录制时间多了约 0.3 ms，因为 pass 和 dispatch 多了。规模场景里大部分球被前面的球挡住，100 万个实例时 GPU 帧快了 5.7 倍。Sponza 少画九成的三角形，可见性光栅化却只少了 0.044 ms：1080p 下它的时间花在像素上，不在三角形上，抵不过固定开销，GPU 帧慢了 0.03 ms；棋盘场景几乎没有遮挡，慢了 0.05 ms。默认开着，因为省下的随遮挡增长，没有遮挡时的损失有上限。固定开销里最大的一项是建金字塔，可以改成一次 dispatch 建好多级。

## P5：分簇光照

`lightgrid=on|off`，规模场景 10 万个实例，点光源的范围是 6，另有一个方向光；同一进程里交替，RTX 5070 Ti，1920×1080，240 帧的环绕。`off` 是一个格子装下所有灯，着色仍走同一个掩码循环，每盏灯的代价与逐灯循环相同。

| 灯 | GPU 帧（网格 / 逐灯） | 着色（网格 / 逐灯） | 分配 | 帧图内存（网格 / 逐灯） |
|---|---|---|---|---|
| 1 | 1.682 / 1.698 | 0.015 / 0.015 | 0.003 | 64.6 / 64.5 MiB |
| 16 | 1.709 / 1.714 | 0.017 / 0.024 | 0.005 | 64.6 / 64.5 MiB |
| 64 | 1.712 / 1.741 | 0.025 / 0.056 | 0.007 | 64.7 / 64.5 MiB |
| 256 | 1.757 / 1.935 | 0.054 / 0.187 | 0.013 | 65.1 / 64.5 MiB |
| 1000 | 1.891 / 2.496 | 0.063 / 0.680 | 0.037 | 66.5 / 64.6 MiB |

逐灯时着色随灯数线性增长，按格子分配后 256 盏以上基本不变。分配的代价取决于调用怎么排：一个调用算一个格子的一个掩码字，起初相邻的调用是同一个格子的不同字，各读 32 盏不同的灯，1000 盏灯时分配要 0.167 ms；改成相邻的调用算不同格子的同一个字，降到 0.036 ms。掩码要是也照这个顺序存，着色时一个像素的字分散在不同的缓存行里，着色从 0.050 ms 升到 0.097 ms，所以掩码仍按格子连续存放。

## P7：规模压力测试

规模场景 100 万个实例、1000 盏灯（另有一个方向光），RTX 5070 Ti，1920×1080，`--moving <n>` 让每帧依次移动 n 个实例。i7-13700KF 是混合架构，渲染线程落到 E 核上时准备时间会翻倍，所以这一节固定在 P 核上测（`taskset -c 0-15`，`tools/run-benchmarks.sh` 里设 `LRENDER_BENCH_CPUS`）；即使这样，移动实例时的准备时间在两次运行之间仍差到 1.5 倍，表里给出两次的范围。时间都是毫秒的中位数，墙钟是一帧从提交到收尾。

| 场景 | 修之前：准备 / 录制 / 墙钟 | 修之后：准备 / 录制 / 墙钟 | GPU 帧 |
|---|---|---|---|
| 静态 | 0.10 / 2.03 / 5.20 | 0.09–0.10 / 2.01 / 5.15 | 3.26 |
| 每帧移动 1 万个 | 32.2 / 2.31 / 38.1 | 4.4–6.2 / 2.4–3.0 / 9.5–12.5 | 3.13–3.19 |
| 每帧移动 10 万个 | 62.7 / 8.46 / 78.0 | 27–36 / 7.7–7.9 / 40–49 | 3.64–3.71 |
| 路径追踪（ray query），每帧移动 1 万个 | 28.5 / 1.55 / 36.6 | 3.2–7.6 / 1.8–3.1 / 10–16 | 3.00–3.17 |
| 路径追踪（软件层次结构），每帧移动 1000 个 | 1481 / 37.2 / 1551 | 1.9 / 1.4 / 7.2 | 3.87–3.96 |

找到的两个随场景规模增长的开销：

1. 有实例变化的帧，`RenderWorld` 重算实例的统计（混合实例数、簇数之和、场景包围盒）时扫一遍所有实例，100 万个要 30 ms 左右，与移动了多少无关。改为按 1024 个实例分块累加，只重算改到的块。
2. 软件层次结构的 TLAS 在任何实例移动时整个重建，100 万个实例在渲染线程上要 1.47 s，GPU 线程再上传约 64 MB 的节点。改为只移动时 refit。refit 每帧改写的节点散在整张表里，起初每一段连续的写是一次上传，录制要 5.8 ms；相距 64 个元素以内的写合成一次之后降到 1.4 ms。

剩下的，列为 `roadmap.md` 的 P8 到 P10：移动实例的代价现在与移动的数量成正比，渲染线程上每个 0.3 到 0.6 µs，每帧移动 10 万个时 GPU 等 CPU，时钟降到了 P3；静态场景 GPU 线程录制一帧 2.0 ms，其中 `vkQueueSubmit` 约 0.4 ms（导出 sync file 只占 0.03 ms），其余是约 110 次 dispatch 的录制；实例增删之后 TLAS 仍整个重建。
